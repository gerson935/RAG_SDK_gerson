01Consultar antes de responder

Dar contexto a la IA.

Un modelo puede conocer conceptos de marketing y, aun así, desconocer lo que ocurrió en una entrevista o lo que dice el informe de un cliente.

RAG significa Retrieval-Augmented Generation: generación aumentada por recuperación. El sistema busca información relevante en una colección y se la proporciona al modelo para que elabore una respuesta.[1, 2]

La colección puede reunir entrevistas, manuales o informes. En una implementación habitual con un modelo por API, consultar esos documentos no exige volver a entrenar el modelo. Lo que cambia es la información que recibe en cada consulta.

¿Por qué no simplemente subir todos los documentos a un chat?

Puede ser una buena solución cuando el material cabe, está bien organizado y el trabajo es puntual. RAG resulta especialmente interesante cuando la colección crece, se actualiza o necesita búsquedas y permisos controlados. La elección depende del caso: conviene comparar calidad, tiempo y costo antes de añadir complejidad.

02Conectar las piezas

De una conversación
a una aplicación.

Una vez que sabemos qué debe hacer el sistema, necesitamos una forma de conectar sus componentes. Aquí aparece el SDK.

Un SDK (Software Development Kit) es un conjunto de herramientas para desarrollar software. Por ejemplo, puede facilitar que un programa solicite una respuesta a un servicio de IA y reciba el resultado.

RAG describe una forma de trabajar con información. Un SDK ayuda a programar conexiones. El SDK no decide por sí solo qué fuentes son fiables ni convierte automáticamente una aplicación en un agente.[3, 4]

El recorrido de una solicitud

Esquema conceptual, sin llamadas reales

La API

Es la interfaz que define cómo solicitar funciones a un servicio y qué respuestas recibir.

El SDK

Ofrece herramientas para utilizar esa interfaz desde un programa, con menos trabajo repetitivo.

La aplicación

Reúne la experiencia completa: documentos, preguntas, reglas, herramientas y revisión.

Una mirada al interior: ¿cómo se expresaría en un programa?

Pseudocódigo ilustrativo. Las funciones representan tareas; no son instrucciones listas para ejecutar ni la API de un proveedor.

pregunta = recibir_pregunta()
fragmentos = buscar_en_documentos_autorizados(pregunta)
respuesta = consultar_modelo(pregunta, fragmentos, reglas)
mostrar_respuesta_y_fuentes(respuesta, fragmentos)
esperar_revision_de_la_persona()

El programa también necesita controlar errores, accesos y costos. Si se conecta a servicios externos, las credenciales deben permanecer protegidas en el servidor, fuera del HTML que se comparte.

¿Dónde entrarían los agentes?

Podría separar tareas de búsqueda, contraste y redacción. Un flujo puede tener pasos definidos; un agente puede decidir qué herramienta utilizar dentro de límites. Empezaría con el flujo más sencillo que resuelva el problema.[4]

¿Y GraphRAG?

Es una opción para organizar y consultar relaciones entre entidades y temas del corpus. La estudiaría para preguntas que necesitan conectar información de distintos documentos. Un mapa visual como el de arriba, por sí solo, no implica usar GraphRAG.[5, 6]

Cómo elegiría la complejidad del proyecto

Compararía alternativas sobre las mismas preguntas y el mismo material. El grafo tendría que justificar el trabajo y el costo que añade.

La investigación comparativa encuentra resultados distintos según las tareas. No asumiría que añadir grafos o agentes mejora cualquier respuesta.[6]

05Lo que quiero comprobar

La calidad está
en poder revisarlo.

Un texto convincente es solo una parte del resultado. Para desarrollar el proyecto, estas serían mis preguntas de evaluación.

¿La fuente sostiene la afirmación?

Comprobar cada conclusión importante contra el fragmento original y mostrar contradicciones cuando existan.

¿Reconoce lo que no sabemos?

Incluir preguntas sin respuesta en los documentos. Una estimación sin base debe quedar identificada, no presentada como un hecho.

¿Ayuda más que el proceso actual?

Comparar el tiempo hasta un entregable aceptable, los errores y las correcciones necesarias, incluyendo la revisión humana.

¿Respeta el contexto del proyecto?

Separar información por cliente y permisos; conservar fechas y versiones; tratar los documentos como datos, no como instrucciones.
